# Todo Quick Add

> 本仓库中的版本已把知识空间 ID、文档 token 和租户域名替换为 `<…>` 占位符，使用前替换为实际值。

## 目标文档

用户的「文档库」知识空间（space_id `<文档库 space_id>`）主目录下的「To Do List」（原名「待办事项」，用户已改名）：

- 父节点：`https://<租户>.feishu.cn/wiki/<To Do List 节点 token>`（主目录顶层，标题「To Do List」）
- **待办清单正文文档**：`https://<租户>.feishu.cn/docx/<待办文档 token>`（其子节点，标题「待办事项」）
- 同级还有「已完成事项」文档（`<已完成事项文档 token>`），本技能不修改它

注意：用户还有另一个空间「仿生智能与具身模型」，那里**没有**待办事项，不要找错。

## 文档结构

正文文档由三个一级标题分区，每个分区下是 checkbox 列表（`<checkbox done="false">事项</checkbox>`）：

| 分类 | 内容特征 | 示例 |
|---|---|---|
| 项目研发 | 技术研发、调研复现、仓库/服务器、机器人与AI相关 | 「每日论文推送」「具身智能API调研」 |
| 日常办公 | 人事、行政、生活手续类事务 | 「党员组织关系转移」「上海落户」 |
| 其他休闲 | 娱乐、追剧、兴趣消遣 | 「短剧：艺一《困兽之战》…」 |

## 执行流程（直接给任务内容）

用户在对话中说「加个待办：xxx」「todo：xxx」「记到待办里」「待办里加一条」，或说「增加待办」这类短指令（任务内容由上下文补全）。输入通常是口语，需要润色，因此同样必须先预览确认。

1. **分类**：根据任务内容判断属于「项目研发 / 日常办公 / 其他休闲」哪一类；用户已指定分类则直接采用。模糊时按上表特征判断，倾向研发技术类内容（用户主业是仿生机器人 AI 研发）。
2. **润色**：把用户原话或上下文中提炼的任务整理成单句（与其他条目风格一致），保留具体型号/规格等关键细节，不扩写多句。
3. **预览确认（必经步骤）**：列出拟添加的待办条目及建议分类，等用户回复。用户提出调整（改措辞、换分类、拆分、合并）就修改后再次预览；用户明确认可（「OK」「可以」「没问题」等）后才写入。用户明确说「直接加」时可跳过预览。
4. **读取最新文档**（必须重新读取，不可沿用旧内容）：
   ```bash
   lark-cli docs +fetch --doc <待办文档 token> --detail full --as user --format json
   ```
5. **定位插入点**：新待办统一插在目标分类 h1 标题的正下方（分区最前，从前往后记、新条目在前）。插入点用 h1 标题的 block id；一次添加多条时，按内容先后顺序依次插在前一条之后。
6. **插入待办**：
   ```bash
   lark-cli docs +update --doc <待办文档 token> \
     --command block_insert_after --block-id <目标分类h1标题的block_id> \
     --content '<checkbox done="false">任务内容</checkbox>' --as user --format json
   ```
7. **确认交付**：告知用户添加到了哪个分类，并给出文档链接。

## 执行流程（从录音/云文档提取待办）

用户用录音豆记录待办，语音自动生成云文档（标题形如「文字记录：soundcore … 日期」或「智能纪要：…」），可能在云盘，也可能在文档库（知识空间）里，两者都可读。用户在豆包侧边栏打开该文档后说「转成待办」「转成一条/两条/N条待办」等触发。

**核心规则：先预览，确认后才写入。用户明确说「直接加」时才可跳过预览。**

1. **获取文档**：优先用会话中当前打开文档的 token（system 提供的 `<url>`），否则用用户给的链接/token。读取：
   ```bash
   lark-cli docs +fetch --doc <录音文档token> --as user --format json
   ```
   - 转写文档格式：引用块含录音主题/时间/智能纪要链接，正文每段为「说话人 + 时间戳 + 内容」，同一段视为一个整体。
2. **提取待办**：从口语内容中提取可执行事项，去除口头语（「然后」「OK 暂时这些」等无信息量内容丢弃）。每条润色为与其他条目风格一致的单句，涉及具体型号/规格的保留细节。
3. **条数**：用户说了「一条/两条/N条」就严格按该条数归纳拆分；没说数量时自行判断合理粒度。
4. **预览确认（必经步骤）**：列出每条拟添加的待办及其建议分类（项目研发/日常办公/其他休闲），等用户回复。用户提出调整（改措辞、换分类、拆分、合并）就修改后再次预览；用户明确认可（「OK」「可以」「没问题」等）后才进入下一步。
5. **写入**：重新 fetch 待办清单拿最新 block id，把达成一致的条目逐条插入对应分类（统一插在分类 h1 标题正下方，多条按内容顺序从前往后排列）。
6. **确认交付**：告知写入结果并附文档链接。

## 规则

- 写入前必须重新 fetch 全文拿最新 block id，防止用户手动编辑后 ID 失效。
- 任务内容用用户原话或轻度润色后的单句，保持与其他条目风格一致；不要自行扩写多句。
- 一次可以添加多条，分别插入对应分类。
- 用户说「完成了某条待办」时：将该 checkbox 的 `done` 改为 `true`（`block_replace`），或按用户习惯移到「已完成事项」文档，不确定时先问。
- 若文档结构发生大改（分类标题变动），以重新 fetch 的实际结构为准并更新本文件中的分类表。
